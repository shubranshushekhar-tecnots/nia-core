Part 1: NiaType and adapter mappings
- NiaType (closed): string (optional format: uuid, objectId), integer, float, decimal (optional precision/scale), boolean, date, timestamp (tz: utc | naive), bytes, json, object { fields }, array<T>. Every field carries nullable; inferred fields also carry presence (the fraction of records that have the field).
- Type join, used wherever types meet: integer ⊔ float = float; integer or float ⊔ decimal = decimal; date ⊔ timestamp = timestamp; object ⊔ object = merged fields; array<A> ⊔ array<B> = array<A ⊔ B>; anything ⊔ null = nullable. A join that falls back to string (e.g. integer ⊔ string) or json (object ⊔ scalar) is marked degraded.
- Each dialect adapter declares both directions, native → NiaType (sources) and NiaType → native (destinations), each marked lossless or lossy with a reason.
  - Postgres: jsonb for json/object/array; native uuid.
  - MySQL: JSON; CHAR(36) for uuid; VARCHAR(255) for string keys; DECIMAL(p,s) when precision is known, otherwise DOUBLE.
  - Mongo: native types; decimal → Decimal128 or double.
- Declared SQL source schemas become NiaSchemas through these mappings.

Plan update (Mongo destination un-flattening, pre-Part-3 fix)
- connector-mongodb already flattens on read: nested plain objects become dotted-path columns (`{a:{b:1}} -> "a.b"`), arrays never descend and stay JSON.stringify'd "json"-typed columns. This predates Part 4's contract work and needed a symmetric write-side fix now rather than waiting for the full destination-contract machinery.
- For Mongo destinations, /write now un-flattens: each column name is split on "." and rebuilt into a nested document (services/connector-mongodb/src/writeOps.ts's unflattenDoc/setNestedPath), and any string value that parses as a JSON array is reparsed back into a real array (maybeParseJsonArray) — narrow by design, mirroring flatten.ts's own narrow "only arrays get stringified" rule, so a legitimate string column that happens to look like JSON (e.g. "123") is left alone. This makes Mongo -> Mongo round-trip the same document shape.
- Degraded columns: a source field name that itself contains a literal "." is ambiguous with the dotted-path nesting convention (can't tell `{"a.b":1}` from `{a:{b:1}}` once both produce column name "a.b"). flatten.ts now flags this case instead of guessing: it stops descending into that key's subtree, treats it as an opaque leaf (JSON.stringify'd if array/object, raw if scalar), and adds it to a new `degradedColumns` set. This is surfaced as a `degraded: boolean` field on `Column` (packages/schemas/src/tabular.ts, used by every connector's /execute TabularResult) and on `IntrospectResponse.entities[].fields` (packages/schemas/src/contract.ts) — both default to unset/false for every connector with no such ambiguity (the SQL dialects).
- Known, accepted limitation: `WriteRequest` carries no column-type or degraded metadata (same gap as Part 2's json round-tripping fix for the SQL connectors) — the write-side un-flatten is a mechanical, unconditional split-on-"." inversion and cannot skip a column that was flagged degraded at read time. The `degraded` flag's value is entirely at read/profile time (for a mapping UI to avoid guessing a nested shape from an ambiguous name); fixing this at write time would require threading degraded-ness through the signed WriteContext, which is out of scope here and deferred to Part 4's destination contract (which already carries a fidelity/degraded flag per column).
- Tests: services/connector-mongodb/src/flatten.test.ts (degraded-flagging cases) and the new services/connector-mongodb/src/writeOps.test.ts (un-flatten + array-reparse cases).

Plan update (Part 3)
- `typeOfExpr` naming collision: `expression.ts` already exports a function named `typeOfExpr(expr: Expr): ExprValueType` (a narrower grammar-well-formedness classifier returning only `"scalar" | "boolean"`, unrelated to NiaType). Rather than overload or rename the existing function, the NiaType-returning version required by this part lives in a new file, `packages/schemas/src/niaExprType.ts`, exporting its own `typeOfExpr(expr: Expr, input: NiaSchema): ExprTypeResult`. Valid since modules are namespaced (both are re-exported from `index.ts` under the same name with no actual clash at any real call site), but noted here since it's a deviation from "add a function called typeOfExpr" read as "extend the existing one."
- `outputSchema` extends this codebase's existing "`""` is a draft/autosave-transient state, not a config error" convention (already used by `ComputedFieldStep.name`, `FilterCondition.field`, `AggregationSpec.alias`) rather than treating an incomplete draft step as an unschemaable failure: `computed_field` (empty `name`), `aggregate` (per-aggregation empty `alias`), `to_json` (empty `field`/`outputName`), and `flatten` (empty `field`) all pass their input schema through unchanged when still mid-draft. Hard failure (naming the column, per the plan's "never guess" instruction) is reserved for genuine unresolvable cases: an unknown field reference, or `flatten` against a non-object-typed field.
- `flatten`'s column naming uses `${prefix}_${key}` (underscore), not dot-joined paths, matching `niaInference.ts`'s existing `normalizeFieldName` convention (Part 2) that nested paths already normalize to underscore-joined destination columns — keeps `flatten`'s schema-time output consistent with how the rest of the pipeline already names flattened columns, rather than introducing a second naming scheme.
- `flatten`'s `outputSchema` also detects and fails on a within-step column-name collision (a flattened child name colliding with an existing sibling column) — a second concrete instance of the plan's "if an output type can't be determined [or is otherwise ambiguous], fail naming the column; never guess" instruction, beyond the plan's own explicit non-object-source case.
- Nullability over-approximation, not precise tracking: `computed_field`'s new field is always `nullable: true` (would require threading onFailure/fallible-call semantics through `typeOfExpr`, which the plan doesn't ask for); `aggregate`'s `avg`/`min`/`max` outputs are always `nullable: true` (an empty group produces no `avg`/`min`/`max` row at all in SQL, but `min`/`max` over an all-NULL group is NULL) while `count`/`count_field`/`count_distinct`/`sum` stay `nullable: false`. Both are safe over-approximations (never asserting non-null when a null is possible), consistent with the codebase's existing tolerance for this class of imprecision (see `computedField.ts`'s own similar comment for the pre-Part-3 precedent).
- `ToJsonStep`/`FlattenStep` (nodeConfig.ts) both omit `onFailure` — neither step is ever row-level fallible. `to_json` accepts any JS value as valid JSON (nothing to fail on at the row level); `flatten`'s "never guess" enforcement happens entirely at schema/compile time via `outputSchema` (non-object source, or a name collision), not as a per-row runtime failure mode — there is no row shape for which `flatten`'s `applyResidual` itself needs an onFailure policy.
- `flatten`'s `applyResidual` computes the flattened extra-columns set as the union of keys actually produced across *every* row, not just the first row — necessary correctness fix for loosely-typed sources (Mongo, JSON) where different rows can genuinely produce different flattened keys under the same `flatten` step; sampling only `row[0]` would silently drop columns that only appear starting on a later row.
- Pushdown for both new ops is deferred to TODO.md, per the plan's own instruction — see TODO.md's "Schema-layer Part 3: pushdown for `to_json`/`flatten`" entry for the specific per-dialect options considered and why they were deferred rather than built now.

Plan update (Part 3 second follow-up — flatten's throw made a clean run-abort, not an uncaught exception)
- Traced what actually happens today when `flattenObjectValue` throws: apps/worker/src/lib/etl/runEtl.ts's three `applyResidualTransforms(Chunk)` try/catch sites only special-case `OnFailureAbortError` (`ops/onFailure.ts`) — anything else is re-thrown, which crosses no clean-abort path. Only the "worker process doesn't crash" and "destination is never touched" halves of the user's ask were already true (BullMQ's Worker catches job-handler rejections itself; the destination write/staging-apply step is unconditionally after the transform step in the pipeline, so an error there is never reached).

- Explicitly reserved `ResidualAbortError` for exactly this class of failure (op author declares "this row's shape can't be handled, abort cleanly"), not a general catch-all: a genuine programming bug in an op should still throw a plain `Error` so it surfaces loudly (BullMQ retries + logs) rather than being silently reported to the user as an expected, clean "run failed" data issue — see the class's doc comment in `onFailure.ts`.

Plan update (Part 4)

This is deliberate, not an oversight: Part 5's implicit conformance step (docs/plans/schema-layer.md's own Part 5 section) is where a step's actual runtime column set gets reconciled against the contract; building that reconciliation twice (once loosely here, once properly in Part 5) would duplicate work with a different shape.
